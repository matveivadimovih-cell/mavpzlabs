# ADR 0002 Вибір підходу опису вимог та матриці трасування
## Контекст і постановка проблеми
В ході роботи після переходу від побудови Use Case діаграми до опису функціональних вимог виникає проблема дублювання інформації між Use Case, User Stories, EARS, Gherkin. 
Тому треба обрати підхід до опису вимог та рівень надлишковості інформації, що допустимий при роботі.
## Розглянуті варіанти
- Варіант 1:
Працювати через формальний опис, створювати окремі вимоги для кожного кейсу.
- Варіант 2:
Працювати через послідовне уточнення, тобто переходити від абстрактніших кейсів до Gherkin для опису сценаріїв та механізмів уточнення, і далі до вимог EARS для опису функціональних вимог, що неможливо виразити через попередні етапи.
## Переваги й недоліки
- Варіант 1:
Плюси:
Створюється єдиний документ з усіма вимогами, які розписані явно, не треба збирати воєдино артефакти для розуміння повної картини, зручно для формальних систем.
Мінуси: Дуже висока надлишковість, матриця значно збільшується в розмірах, складно підтримувати та синхронізувати при постійній зміні вимог.
- Варіант 2:
Плюси: Немає надлишкового дублювання, що підвищує щільність інформації, зберігається фокус саме на бізнес-логіці, значно компактніша матриця трасування, легше підтримувати при постійній зміні вимог.
Мінуси: Усі вимоги розподілені між декількома артефактами, матриця трасування може не мати стовпців для тривіальних кейсів, шо треба обгрунтовувати.
## Результат рішення
Обрано варіант 2 (послідовне уточнення), оскільки в системі бібліотеки присутні тривіальні операції, що не несуть ризиків для системи, а також постійна зміна та уточнення вимог у ході роботі, що вимагало б їхнє переписування, що в свою чергу збільшувало ризик розсинхронізації у роботі, плутанину. Тепер зусилля можуть бути сфокусовані на уточненні вимог, правил роботи з сервісом, логіці переходів стану екземплярів тощо.
## Наслідки
Позитивні:
Специфікація стає компактною, матриця трасування відображає реальні залежності.
Мінуси:
Стовпці деяких кейсів залишаються непокритими, що зафіксовано та обгрунтовано у requirements.md.
